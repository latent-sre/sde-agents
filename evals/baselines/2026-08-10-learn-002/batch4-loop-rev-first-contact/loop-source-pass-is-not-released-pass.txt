**The two distinct result classes**

1. **Source evaluation** — the eval suite run against the canonical change in the source tree (post-merge, adapters regenerated to parity). This class answers: *is the fix logically correct and does it hold across the adapter surface as authored?* It's necessary, it's fast to get, and it's what passed here.
2. **Released-artifact retest** — the same (or equivalent) eval run against the actual packaged plugin version a user installs. This class answers a different question: *did the fix survive packaging, versioning, and the release pipeline intact, in the form users actually get?* Source PASS does not entail this — build steps, adapter-generation-at-release-time, dependency pinning, or a version bump that didn't include the commit can all silently break the chain between "merged" and "shipped correctly." These are not redundant checks; they cover different failure surfaces, and only the second one is evidence about what the reporter's issue was actually about (their observed, running behavior).

1. A plugin version must ship that includes this canonical change (a release, not just a merge).
2. A released-artifact retest must be run against that shipped version and its result recorded.
3. That retest must report PASS (parity with the source eval) before the field issue is closed as fixed.
