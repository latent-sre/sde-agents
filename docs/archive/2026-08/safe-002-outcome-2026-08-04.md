# SAFE-002 outcome: effect-broker unknown-outcome reconciliation

**Status:** landed 2026-08-04 on the SAFE-002 round branch.
**Source:** the roadmap's SAFE-002 item, from the accepted
[`AI graph engineering decision`](../../decisions/2026-07-31-ai-graph-engineering.md) and the defect
confirmation in the
[`2026-07-31 independent review`](../2026-07/graph-decision-independent-review-2026-07-31.md).

## The defect

The broker reserved an approval's nonce before dispatch and finalized the row afterward. A crash
between those points — before dispatch, mid-dispatch, or after dispatch but before finalization —
left a permanent `reserved` row whose external outcome was unrepresentable: it blocked replay by
accident of the primary key, but nothing could distinguish "in flight" from "crashed", and no
operator path existed to see or close the ambiguity.

## What landed

- **An explicit `unknown` state with three recorded origins.** In-process deaths are captured at
  the point they occur: a runner exception marks `dispatch-exception`, a failure after the runner
  returns (envelope construction or the finalizing ledger write) marks `finalization-exception`,
  and both re-raise afterward. Whole-process deaths (SIGKILL, host loss) leave a `reserved` row
  that the next sweep marks `stale-reservation`. The origin tells the reconciling operator how far
  the broker reached.
- **A staleness sweep keyed on process identity, not time.** Reservation and finalization happen
  inside one broker process, so every execution and every `reconcile` run first promotes any
  `reserved` row owned by a different pid to `unknown`. The owning-pid exemption — rather than a
  clock threshold — is what keeps concurrent consumers in one process from promoting each other's
  live reservations; the pre-existing concurrent-consumer test passes unchanged.
- **An operator reconciliation path.** `effect_broker.py reconcile` sweeps and lists every
  unresolved reservation with its exact approved action, target, and argv (copied into the ledger
  at reservation time so the listing is self-sufficient). `effect_broker.py resolve` records the
  operator's resolution — resolver, timestamp, one of `applied` / `not-applied` / `indeterminate`,
  and a required note — into the row. `unknown` is terminal until then: only `unknown` rows may be
  resolved, resolved rows cannot be re-resolved, and no state ever becomes replayable.
- **Crash-marking is best-effort by construction.** A failed mark never masks the crash that
  triggered it; the row simply stays `reserved` until the next sweep. The mark uses the wall clock,
  not the caller's injected time source, so failure handling never depends on a clock that may be
  part of the failure.
- **Pre-existing ledgers migrate in place.** The reconciliation columns are added by idempotent
  `ALTER TABLE` at open; legacy rows keep their data, and a legacy `reserved` row's NULL pid is
  always stale (the upgrade itself means its process is gone). Rejecting an old ledger would have
  destroyed the consumption history an operator needs for exactly the crashes being repaired.
- **Promotions surface in execution evidence.** When a sweep promotes rows at the start of an
  execution, that execution's evidence envelope carries one limitation line naming the count and
  request ids, so an operator reading the envelope learns that ledger repair happened.

## Choices a future round should not relitigate

- **Resolution evidence lives in the ledger row, not a separate envelope.** The ledger is already
  the system of record for consumption evidence (it holds the execution `evidence_id`); a second
  artifact would split one audit trail across two stores.
- **Agent contracts are unchanged.** Reconciliation is an operator function, and the agent's
  boundary — prepare requests only, never approve or execute — is exactly what it was. No
  canonical definition was edited, so no adapter regeneration or routing eval was owed.
- **No version bump.** Version choice is an operator-ruled release act (the 1.6.10 ruling); this
  repair ships with the next release, and merged-not-released is LOOP-001's explicit subject.

## Discovery routed at closeout

The roadmap's SAFE-003 next action planned to decide resolver-vs-enforce "when SAFE-002 opens
`run_state.py` anyway" — a wrong premise: SAFE-002's repair lives entirely in `effect_broker.py`,
which owns its own ledger and never opens `run_state.py`. Disposition: doc-found-wrong, fixed at
the owning artifact (the roadmap's SAFE-003 next action now stands alone). No reusable lesson
retained — a one-off factual slip, not a recurring failure shape.
