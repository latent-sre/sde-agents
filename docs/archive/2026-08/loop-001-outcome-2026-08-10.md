## What landed

- **Fields, not new lifecycle states** — the design decision the spec left to the plan. The
  merged≠released distinction lands as optional record blocks on a promoted candidate
  (`release`: version, reference, recorded_at; `retest`: result, environment, reference,
  recorded_at), because new `promotion_state` values would have rippled through the three
  declared STATE_DISPOSITIONS mirrors, the packet grammar, and every learning contract —
  violating the no-grader-loosened constraint for no added power.
- **`record-release` / `record-retest`** in `scripts/learning_ledger.py`, fail-closed:
  release only on a `promoted` candidate, retest only after a release, double-release refused
  (a later release is a new record's business — re-promotion archives the prior blocks to
  `release_history`, and a stranded history with no current release is a reader-rejected
  ledger, not a warning). A `fail` retest prints the loud regression pointer and surfaces in
  the `regressed` view until the owner records a disposition transition whose `reason` field
  is the durable trigger record — the spec's rollback-trigger clause carried by the lifecycle
  rather than a third block.
- **Pull-based discovery**: `list --view awaiting-release` / `awaiting-retest` — a release or
  upgrade retro reads them; nothing schedules anything (the no-new-machinery non-goal held:
  no scheduler, daemon, transcript store, or self-modifying loop).
- **The closure rule** in `skills/self-improve-loop`: a field-feedback item closes as
  successful only with an exact released-version retest recorded, or the owner's explicit
  reason it is impossible; source-eval PASS is never reportable as released PASS. The full
  lifecycle statement governs from `references/learning-ledger.md`.
- **Issue-side visibility**: `.github/ISSUE_TEMPLATE/field-feedback.md` makes the minimum
  contract (owner, target release, eval evidence, released version, downstream retest)
  visible where issues are the destination — a template, not a bot; issues remain intake
  under docs rule 7.
- **Three behavioral contracts** (`loop-capture-is-not-closure`,
  `loop-duplicate-merges-provenance`, `loop-source-pass-is-not-released-pass`) — issue #67's
  Evals 1–3, positives-first graders. Evals 4–5 were owned by GATE-001 (closed); Evals 6–7
  are covered by the existing promotion-gate and sensitivity contracts, as the plan records.

## Rollback truth (corrected during review)

The code reverts in one commit, but records are data: any candidate that gained
`release`/`retest`/`release_history` blocks must have them stripped in the same change or the
restored reader rejects the ledger on every command. `learning/README.md`'s Rollback section
is the executable procedure. The plan's original one-revert claim was corrected when review
proved it false.
